### Issue 1 — TypeScript and typescript-eslint Version Conflict During Dependency Installation

**Phase:** Project Setup / Foundation  
**Status:** Observed in terminal log.  
**Severity:** High — blocks `npm install`.

**AI Failure:**

The AI instructed the user to initialize the project with:

```bash
npm create vite@latest . -- --template react-ts
```

However, it did not check whether the TypeScript version generated by the Vite template was compatible with the peer dependency requirements of the TypeScript ESLint tooling.

**Evidence from the conversation transcript:**

The `npm install` command returned `ERESOLVE unable to resolve dependency tree` with the following details:

```text
Found: typescript@7.0.2

Could not resolve dependency:
peer typescript@">=4.8.4 <6.1.0" from typescript-eslint@8.72.1
```

**Impact:**

npm could not resolve the dependency tree, so project installation was blocked. This was a dependency compatibility issue, not a React source-code error.

**Proposed Fix:**

1. Change the TypeScript version in `package.json` from `~7.0.2` to `~5.9.3`.
2. Remove the `node_modules` directory and the `package-lock.json` generated by the failed installation.
3. Run `npm install` again.
4. Verify the installed versions using:

```bash
npm list react react-dom typescript typescript-eslint
```

**Verification Status:**

The transcript contains the proposed fix, and a later project snapshot shows `node_modules` and `dist` directories. However, it does not contain the actual `npm install` output after the version change. Therefore, complete resolution has not been independently confirmed.

**Lesson Learned:**

Do not assume that the latest version generated by a project template is compatible with the entire toolchain. Check peer dependency requirements and verify the installation with `npm install`, `npm run lint`, and `npm run build`.

### Issue 2 — Leaderboard Uses Hardcoded IDs Instead of `useId()` for Labels and Controls

**Phase:** Phase G — Leaderboard  
**Status:** Found during static code review.  
**Severity:** Medium — violates the project's accessibility requirements.

**AI Failure:**

The AI-generated Leaderboard component used hardcoded IDs:

```tsx
<label htmlFor="squad-search">Search squad</label>
<input id="squad-search" ... />

<label htmlFor="leaderboard-sort">Sort by</label>
<select id="leaderboard-sort" ...>
```

However, the project's rules explicitly require every input and select to have a corresponding label, with IDs generated using React's `useId()`.

**Impact:**

With only one Leaderboard instance, the labels currently point to the correct controls. However, hardcoded IDs can become duplicated if multiple Leaderboard instances are rendered on the same page. This can break the uniqueness of label-control relationships and does not comply with the project's accessibility requirements.

**Required Fix:**

Import `useId` from React and generate two IDs inside the component (`searchId` and `sortId`). Use these generated IDs consistently for the corresponding `htmlFor` and `id` attributes.

Do not reuse hardcoded ID strings.

**Suggested Tests:**

- Render two Leaderboard instances on the same page.
- Verify that all IDs in the DOM are unique.
- Click each label and confirm that focus moves to its corresponding input or select.
- Verify keyboard navigation using the Tab key.

**Verification Status:**

The transcript contains the original code with the hardcoded IDs. However, it does not confirm that the fix was applied or that accessibility tests were performed. Therefore, the issue is not marked as fixed.

**Lesson Learned:**

Do not only verify that filtering and sorting work. AI-generated code must also be checked against the complete Code Contract and accessibility requirements before committing.

### Issue 3 — Shared Claim Status Can Be Overwritten When Two Drops Are Claimed Concurrently

**Phase:** Phase E — Optimistic Claim Hook  
**Status:** Risk requiring testing; identified through code-flow analysis.  
**Severity:** Medium — can display a status message that does not correspond to the correct drop.

**AI Failure / Risk in the Generated Code:**

The hook uses one shared string state:

```tsx
const [claimStatus, setClaimStatus] = useState('');
```

Meanwhile, the request lock is maintained separately for each `dropId`:

```tsx
const inFlightRef = useRef<Set<string>>(new Set());
```

This means two different drops can be claimed concurrently. Each request updates the same `claimStatus` state. The request that updates the state last can overwrite the status message produced by the other request.

In the provided `App.tsx`, the same `claimStatus` is also passed to every `DropCard`.

**Potential Impact:**

When the VIP Ticket and G-Coin Crate are being claimed at nearly the same time, the interface may display only the result of whichever request updates the shared state last. Users may not know which drop the message belongs to, or may miss the result of the other request.

**Recommended Fix:**

Choose one of the following designs and apply it consistently:

- Manage claim status by `dropId` (for example, using a record or map of statuses), so each card displays its own result.
- If the interface should allow only one claim at a time, use a global request lock to prevent another claim while the first request is running.

For a design that allows multiple drops to be claimed concurrently, managing status by `dropId` is the more appropriate approach.

**Suggested Tests:**

1. Claim both drops almost simultaneously.
2. Make one request succeed and the other return HTTP 409.
3. Verify that stock is rolled back for the correct drop.
4. Verify that each card displays the correct status.
5. Repeat the test with the request completion order reversed.

**Verification Status:**

This risk is inferred from the state and locking structure in the provided code. The transcript does not contain evidence of a concurrent browser test, so it is not recorded as a bug that has already been reproduced in the browser or DevTools.

**Lesson Learned:**

When request locks are maintained per resource, the corresponding result state should also be designed per resource, unless the application intentionally restricts requests to one global operation at a time.

## 3. Unsafe Git Instruction Identified Before It Caused an Impact

### AI Suggested `git add .` While the Working Tree Contained Unrelated Changes

**Phase:** Commit After Phase E / UI Integration  
**Status:** Observed in the transcript; identified before staging.  
**Severity:** High — workflow risk that could cause unrelated files to be included in a commit.

The AI suggested running:

```powershell
git add .
git commit -m "feat: implement PUBG crate drop claiming"
```

However, the `git status` output immediately afterward showed multiple modified and untracked files, including files belonging to other phases, project documentation, configuration files, and a ZIP file located outside the current project directory.

Therefore, `git add .` could have staged unrelated files and violated the project's atomic commit workflow.

**Safe Approach Used Later:**

Only stage the file belonging to the specific task, inspect the staged file list with `git diff --cached --name-only`, and then commit.

For example, for Task E1:

```powershell
git add -- src/hooks/useOptimisticClaim.ts
git diff --cached --name-only
git commit -m "feat(claim): add optimistic crate claim hook"
```

**Actual Impact:**

The transcript shows that after the suggestion to use `git add .`, Git still reported:

```text
no changes added to commit
```

Therefore, there is no evidence that `git add .` was actually executed or that an incorrect commit was created. This was an unsafe AI instruction identified before it caused a change.

**Lesson Learned:**

For an atomic commit workflow, never recommend `git add .` when the working tree contains files outside the current task's scope. Always stage specific paths and inspect the staged diff before committing.
